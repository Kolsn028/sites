# Как вносить изменения

## Четыре границы

1. **Интерфейс**: forms/, commands.py, events.py, tiers.py и другие панели читают ввод и отправляют ответы. Кнопки и модальные окна сохраняют прежние custom_id.
2. **Действия**: services/applications.py выполняет приём/отказ; services/leave.py управляет ролями отдыха; services/ranks.py выдаёт Main и заменяет тиры. Они не формируют embed и не отвечают на interaction. Сложные сценарии переносятся постепенно: например, обзвон и публикация заявок пока остаются в существующих обработчиках.
3. **Права**: access.py хранит решения о допуске. roles.py содержит описание ролей, выбор адресатов и совместимые импорты. Права проверяются при выполнении действия, а не только при отображении кнопки.
4. **Данные**: repositories/ предоставляет именованные методы через прежний Database. SQL убран из основных модулей форм, команд, МП, тиров, повышений, отпуска, личных карточек и очереди. Схема, миграции и формат снимков не изменены. Старые служебные процессы и транзакции roster остаются отдельными.

## Заявка в семью

Форма создаёт заявку → рекрутер берёт её → сервис проверяет актуальную запись и права → выдаёт Colombo + Test, снимает Guest → одна транзакция записывает решение и статистику → интерфейс публикует результат.

Сервис использует блокировку application_action по серверу и ветке. Существующие обработчики сохраняют внешнюю recruiter_decision; обратного порядка захвата нет. Блокировка SQLite не удерживается во время запросов Discord. Вызовы методов записи repositories не нужно повторно оборачивать в db.lock.

Discord и SQLite не образуют общую транзакцию: при частичном сбое ролей заявка остаётся открытой, роли можно довыдать повторно. При сбое статистики транзакция откатывает решение. Ошибка уведомления после сохранения не отменяет решение и не должна приводить к повторному подсчёту. Автоматическая повторная отправка такого уведомления здесь не добавлена.

## Исключения прав

- Тиры: только tiercheck на настроенном сервере, без обхода владельцем, Administrator или старшими ролями.
- Setup, отдых, управление МП, просмотр личных дел: High и выше / владелец согласно существующим правилам.
- Проверка заявок/отчётов и повышения до Main: Recruit и старшие роли.
- Переопределение ответственного по старому can_manage: Leader, Deputy, владелец или Administrator; для решения также нужен доступ рекрутера. High без дополнительных прав не получает этот обход.
- Подтверждение участия: организатор с High+, либо Leader/Deputy/владелец.

## Проверки

Из корня бота: `python -m unittest discover -s tests`.

- test_application_scenarios.py: подача, ответственное лицо, решение, роли, статистика, история, повтор/гонка, потеря прав, ошибки Discord/SQLite и повтор после перезапуска базы.
- test_access_policy.py: сочетания ролей, исключения, первоначальная настройка.
- test_repository_scenarios.py: МП → отчёт → подтверждение → личное дело, изоляция серверов, откат записи, очередь тиров и отсутствие SQL в основных UI-модулях.
- Существующие тесты продолжают проверять отпуск, Main, тиры, снимки данных и persistent views.

Тесты используют временный SQLite и имитацию Discord. Они не заменяют проверку на тестовом Discord-сервере. Для этого структурного изменения не нужен сброс данных или повторный /setup.
